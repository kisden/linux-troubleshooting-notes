每轮实操前的工作流固定为三步：启动虚拟机，用 `command -v` 逐个确认 df、du、lsof、truncate 等工具就位；关机后打干净快照（QEMU 运行中改磁盘元数据会损坏镜像，必须先 `sudo poweroff` 再 `snap`）；开机采集基线数据（df -h / df -i / 监听端口 / 运行中服务 / SUID 文件清单）存入 `~/baseline`。基线的唯一用途是回答「什么是异常」——后面所有判读都以表中的基线值为参照，凡是 Use% 或 IUse% 偏离基线，就是有东西在增长。

## 2. 核心底层原理

### 2.1 一句话原理：df 统计的是「块」，du 统计的是「目录项」

df 读取文件系统的超级块元数据，它只知道「这个分区有多少数据块被占用」；du 则遍历目录树，把每个文件的大小累加出来。两者统计口径不同，在特定情况下必然对不上——而对不上的地方，恰恰就是故障的藏身处。

| 现象 | df -h | du -sh /* | 可能原因 |
|---|---|---|---|
| 两者基本一致 | 占用高 | 某个目录也很大 | 正常情况：真的有文件占着空间 |
| df 高、du 很小 | 占用高 | 各目录都很小 | 已删除但被进程持有句柄（lsof +L1 可见） |
| df 有余量但写不进 | 占用低 | 都很小 | inode 耗尽（df -i 显示 100%） |
| df 与 du 都对不上且无进程 | 异常 | 异常 | 同一目录被重复挂载，挂载点覆盖了原内容 |

### 2.2 磁盘满的三种完全不同的形态

新手最大的误区是把三种形态当成一种，用同一种方法（删文件）去修三种不同的病。

| 形态 | 本质 | 判定命令 | 判定依据 | 正确修复 |
|---|---|---|---|---|
| 容量耗尽 | 数据块被占满 | df -h | Use% = 100% | 删/移走大文件，或扩容 |
| inode 耗尽 | 文件数量达到上限 | df -i | IUse% = 100%，而 df -h 仍有余量 | 清理海量小文件（如 session、缓存） |
| 删除未释放 | 数据块仍被进程引用 | lsof +L1 | df 高、du 低，lsof 能看到 (deleted) | 重启占用进程，或对活文件用 truncate |

### 2.3 排障五步法

排障不是逐个试命令，而是「观察信号 → 生成假设 → 验证假设 → 定位根因 → 沉淀预防」。第一步的产出必须是一条能出数字的命令输出，而不是一句「磁盘满了」。

| 步骤 | 产出 | 举例 |
|---|---|---|
| 1 观察 | 一条带数值的输出 | df -h / → Use% 100% |
| 2 假设 | 1–3 个可验证的陈述句 | 是容量耗尽，而不是 inode 耗尽 |
| 3 验证 | 一条能证伪的命令 | df -i / → IUse% 6%，假设 2 被排除 |
| 4 根因 | 哪个对象、因为什么 | /var/fill 这个 15 GB 填充文件占满根分区 |
| 5 预防 | 一条可执行的措施 | logrotate + 磁盘 85%/95% 双阈值告警 |

### 2.4 为什么第一组命令必须是 df -h 与 df -i 一起看

这两条命令的输出是互斥的判决书：一个满、另一个不满，就能直接锁定形态，不需要任何猜测。只看 df -h，你会想「删点东西」；只看 df -i，你会想「文件太多」。两条一起看，10 秒内决定往哪个方向走——这就是「先量化、再动手」的具体含义。

## 3. 分故障实操记录

> 每个故障记录「第几条命令命中根因」（从敲下的第一条排查命令算起，第几条命令让你确定了根因）。**3 条以内算熟练，5 条以上说明在穷举。**

### 3.1 故障 ①：磁盘容量被写满

**标准复现方案**——dd 持续写入填充文件直到空间耗尽：

```bash
sudo dd if=/dev/zero of=/var/fill bs=1M count=20000 2>&1 | tail -5
```

可用空间只有十几 GB，这个量级的 dd 会一直写到没地方为止，自行停下并报 `dd: error writing '/var/fill': No space left on device`。

**本次实操**：以 `bs=1M count=16000` 执行，dd 在 32.1 秒内正常写完并退出（522 MB/s），**并未出现 No space left 报错**——故障表现为「写满后 df 的 Avail 归零、Use% 100%」，而不是 dd 自身中断。随后从普通用户视角写入才复现报错：

```bash
touch /tmp/test.txt
# touch: cannot touch '/tmp/test.txt': No space left on device
```

这一先后关系说明：**注入动作成功了，现象要靠另一个写操作才暴露。**

**排查流程**（按顺序，不要跳步）：

```bash
df -h /            # 第一步：看 Use%，判断是不是容量
df -i /            # 第二步：看 IUse%，排除 inode
sudo du -sh /var/* 2>/dev/null | sort -h | tail -5   # 第三步：谁占的
sudo lsof +L1 2>/dev/null | head                      # 第四步：有没有已删除未释放
```

| 命令 | 应该看到 | 它排除了什么 |
|---|---|---|
| df -h / | Use% 100%（或 99%） | 确认容量确实耗尽 |
| df -i / | IUse% 只有个位数 | 排除 inode 耗尽 |
| du -sh /var/* | /var/fill 排在最后，约 15 GB | 定位到具体对象 |
| lsof +L1 | 无输出 | 排除「删了没释放」 |

实测判读：Use% 100%、Avail 0；IUse% 6%；du 抓到 /var/fill 占 16 G；lsof +L1 无输出（四条命令的完整终端截图本次未收录于笔记，关键数值以 3.5 节判定对照表为准）。第 3 条命令（du）命中根因，耗时 3 min，首次假设正确。

**根因**：/var/fill 单个填充文件 16 GiB 占满根分区（dd 写 16000 MiB，耗时 32.1 s，522 MB/s）。

**修复**：

```bash
sudo rm -f /var/fill
df -h /                          # 应回到基线值（约 27%）
touch /tmp/test.txt && echo 写文件恢复正常
rm -f /tmp/test.txt
```

实测恢复后 df 回到 26%（与基线一致），未回滚快照。

**预防**：

- 磁盘使用率双阈值告警：85% 警告 / 95% 严重（超过 85% 后日志轮转与临时文件容易失败，留 15% 人工处置窗口）
- 根分区可用绝对值告警：< 2 GB（百分比在小分区上会失真：22 GB 的 5% 只有 1.1 GB）
- 写满后不要重启机器——根分区 100% 时 journald、systemd 写不进状态文件，会卡死在启动阶段；真进不去就回滚快照

### 3.2 故障 ④：日志暴涨吃掉磁盘

**标准复现方案**：

```bash
sudo bash -c 'yes "ERROR disk quota exceeded" | head -c 500M >> /var/log/syslog'
ls -lh /var/log/syslog
df -h /
```

500 MB 是刻意限制的量。真实环境里日志是持续增长，症状相同但更隐蔽：df 每小时涨几个百分点，等你发现时已经 100%。

本次实操先后注入 500 MB 与 300 MB 两轮日志。

**排查流程**（定位增长源）：

```bash
sudo du -sh /var/log/* | sort -h | tail -5
sudo du -h /var/log/syslog        # 单个文件的确切大小
```

第一条排查命令为 `ls -lh /var/log/syslog`，第 3 条命令命中根因，耗时 12 min（含二次注入复现与 truncate 对比），首次假设正确。

**根因**：应用持续追加 ERROR 日志，syslog 单文件涨到 501 MB；logrotate 只有 `weekly + rotate 4`，无 maxsize，控制不住单文件膨胀。实测 truncate 前 syslog 为 301 MB、Used 5.6 GB（27%）。

**修复——不要用 rm**：

```bash
sudo truncate -s 0 /var/log/syslog
ls -lh /var/log/syslog
df -h /
```

为什么不能 rm：/var/log/syslog 被 rsyslog 进程一直打开着。rm 只是删掉目录项，数据块要等进程关闭句柄才回收，于是 df 一点也不降——这正是 3.4 节专门演示的形态。`truncate -s 0` 把文件截断为 0 字节但保留 inode，进程继续往同一个文件写，空间立刻释放。

实测：truncate 后 syslog 降到 0 字节，Used 5.6 GB → 5.3 GB（27% → 26%），释放量与文件大小一致。注意本节根分区还有 16 GB 余量，所以写入一直正常——如果是根分区 100% 时才做 truncate，效果会更直观。

**预防（治本：logrotate）**：

```bash
cat /etc/logrotate.d/rsyslog
grep -E "rotate|size|daily|maxsize" /etc/logrotate.conf
```

基线要求：按日轮转 + 保留 7 份 + 单文件上限。当前值：`weekly + rotate 4 + compress + delaycompress`（无 maxsize）——部分符合，缺单文件上限。

监控上再加两道：日志单文件 > 100 MB 告警（正常日志一天几十 MB，单文件破百说明异常刷屏）；日志增长速率 > 50 MB/min 告警（按速率才能区分「本来就这么大」和「正在暴涨」）。另外记住：日志暴涨只是表征，持续刷屏的 ERROR 说明上游有服务在反复失败——用 journalctl 找出刷屏的 unit（见 6 节问答 3）。

### 3.3 故障 ②：inode 用尽

**标准复现方案**（loop 设备 + 人为限制 inode 总数，隔离性好）：

```bash
sudo dd if=/dev/zero of=/root/small.img bs=1M count=200
sudo mkfs.ext4 -F -N 500 /root/small.img      # 关键：把 inode 总数限制为 500（-F 必须加，否则等待确认像死机）
sudo mkdir -p /mnt/small
sudo mount -o loop /root/small.img /mnt/small
df -h /mnt/small;  df -i /mnt/small
sudo bash -c 'for i in $(seq 1 600); do : > /mnt/small/f$i 2>/dev/null || { echo 第$i个失败; break; }; done'
df -h /mnt/small     # 容量还空着
df -i /mnt/small     # inode 已经 100%
sudo touch /mnt/small/newfile    # 报 No space left on device
```

标准方案的恢复方式：

```bash
sudo umount /mnt/small
sudo rm -f /root/small.img
```

**本次实操方案**：未使用 loop 设备，而是直接在根分区的独立目录 ~/inode_test 中批量创建空文件：

```bash
seq 1 1000000 | xargs touch
```

IUse% 由 6%（87083）升至 23%（330984），df -h 全程稳定在 26%——**「容量没变、inode 在涨」这一对矛盾可以同时成立。** 共创建 24.3 万个空文件。

**现象**：df -h 有余量但写不进。本次未推进到 inode 100%，没有复现真实的 No space left 报错——这条留待下次补齐。

**排查流程**：第 2 条命令命中，耗时 6 min，首次假设正确。

```bash
df -h /    # 容量正常：26%
df -i /    # IUse% 23%，远超基线 6%
```

**根因**：~/inode_test 目录批量创建 24.3 万个空文件，消耗 inode（总量 1,458,176，IUse% 峰值 23%，未达 100%）。

**修复**：

```bash
rm -f file_*                                                # 实测失败：Argument list too long
find . -maxdepth 1 -type f -name "file_*" -delete           # 清理后 IUse% 回到 6%（87082）
```

实测踩坑：`rm -f file_*` 直接报 `Argument list too long`——shell 把 `file_*` 展开成 24 万个参数，超过内核参数长度上限。改用 `find ... -delete` 后恢复基线。

**预防**：inode 使用率必须单独监控（85% 告警）——inode 用尽的表现和容量无关，只跟在磁盘使用率后面监控必然漏报。

对比记忆：把本故障与故障 ① 的 df -h / df -i 两组数字并排放——同一个报错、两条命令给出相反结论。这个对比能脱口而出，就是面试题「df 说满了但 du 加起来不多」的完整答案。

### 3.4 故障 ③：删除但未释放——df 与 du 对不上

**标准复现方案**：

```bash
sudo dd if=/dev/zero of=/var/tmp/held.log bs=1M count=800
sudo tail -f /var/tmp/held.log &     # 让一个进程持有句柄
sudo rm /var/tmp/held.log
df -h /                # 已用空间没下降
sudo du -sh /var/tmp   # 但目录变小了
sudo lsof +L1 | head   # 看到 (deleted) 的文件
```

若按标准方案用 held.log 复现，lsof 会显示 tail 进程与 held.log；释放命令：

```bash
sudo pkill -f "tail -f /var/tmp/held.log"
df -h /                # 空间立刻回来
```

**本次实操**：直接删除被 rsyslogd 持有的 /var/log/syslog——删除前后 df 均为 Used 5.8 GB / Avail 15 GB / 28%，空间一点没降。关键证据输出：

```
rsyslogd 637 syslog 7w REG 253,0 524616496 0 1537 /var/log/syslog (deleted)
```

证明约 500 MB 数据块仍被该进程占用。**这条输出是全文最值得记住的一张证据。**

**排查流程**：第 2 条命令命中（df -h → lsof +L1），耗时 2 min，首次假设正确。

**根因**：syslog 被 rsyslogd（PID 637）持有句柄，rm 只删目录项，数据块未回收。

**修复**：结束持有句柄的进程（实测释放 rsyslogd 句柄后空间恢复；具体释放命令原文未记录，等价操作见 2.2 节形态表「重启占用进程」）。

**修复方式对比**：

- ❌ `rm /var/log/syslog`：删掉目录项，句柄还在，空间不释放，必须重启进程
- ✅ `truncate -s 0 /var/log/syslog`：清空文件内容，保留文件和句柄，空间立刻释放，不用重启服务

**预防**：定时巡检 `lsof +L1 | wc -l`，> 0 且 df 与 du 差值 > 1 GB 时告警——空间泄漏最隐蔽的一种。

### 3.5 三种形态判定对照

这是全文核心的一张表，四类故障的实测数字都在这里——只看这张表就应能区分三种「写不进去」。

| 判据 | ① 容量耗尽 | ② inode 耗尽 | ③ 删除未释放 |
|---|---|---|---|
| df -h / 的 Use% | 100%（Avail 0，21 G / 22 G） | 26%（容量始终有余量） | 28% → 28%（删除前后不变） |
| df -i / 的 IUse% | 6%（87083 / 1458176） | 23%（330984，峰值） | 6%（87082） |
| du 与 df 是否一致 | 一致：du 抓到 /var/fill 占 16 G | 一致：各目录都很小，却写不进 | 不一致：df 5.8 G，/var/log 已明显变小 |
| lsof +L1 是否有输出 | 无输出 | 无输出 | 有输出：rsyslogd 637 syslog 7w REG … /var/log/syslog (deleted) |
| 一句话根因 | 数据块被 16 GiB 填充文件占满 | 文件数量（inode）被海量小文件消耗 | 已删除文件仍被进程持有，数据块未回收 |

单次排障汇总（定位耗时按终端文件时间戳 syslog 20:05 → 20:17 与命令序列还原，未用秒表单独计时；① 与「删除未释放」为命令顺序推算的估计值）：

| 故障 | 第一条命令 | 第几条命中 | 耗时 | 首次假设 | 恢复方式 |
|---|---|---|---|---|---|
| ① 容量写满 | df -h / | 3 | 3 min | 正确 | rm -f /var/fill + df 复核 |
| ④ 日志暴涨 | ls -lh /var/log/syslog | 3 | 12 min | 正确 | truncate -s 0 |
| ② inode 满 | df -h / | 2 | 6 min | 正确 | find -delete 清理 24.3 万文件 |
| ③ 删除未释放 | df -h / | 2 | 2 min | 正确 | 释放 rsyslogd 句柄 |

|---|---|---|---|
| ① | 1116-clean | 否 | rm -f /var/fill 就地恢复，df 回到 26% |

### 3.6 预防落地：监控、配置基线与巡检脚本

| 监控项 | 采集命令 | 告警阈值 | 阈值依据 | 可提前发现的故障 |
|---|---|---|---|---|
| 磁盘使用率 | df -h / | 85% 警告 / 95% 严重 | 超过 85% 后日志轮转与临时文件容易失败，留 15% 人工处置窗口 | ① |
| inode 使用率 | df -i / | 85% 警警 | inode 用尽的表现和容量无关，必须单独监控 | ② |
| 日志单文件大小 | du -sh /var/log/* | 单文件 > 100 MB | 正常日志一天几十 MB，单文件破百说明有异常刷屏 | ④ |
| 日志增长速率 | 两次 du 相减 / 间隔 | > 50 MB/min | 按速率才能区分「本来就这么大」和「正在暴涨」 | ④ |
| 已删除未释放 | lsof +L1 \| wc -l | > 0 且 df 与 du 差值 > 1 GB | 空间泄漏最隐蔽的一种 | ③ |
| 根分区可用绝对值 | df -h / \| awk 'NR==2{print \$4}' | < 2 GB | 百分比在小分区上会失真：22 GB 的 5% 只有 1.1 GB | ① |

配置基线检查表：

## 4. 误判与踩坑复盘

### 4.1 实际发生的两次误判

| # | 最初以为是 | 实际是 | 为什么误判 | 以后怎么避免 |
|---|---|---|---|---|
| 1 | 删不掉 inode_test 里的文件是权限问题或文件系统故障 | shell 把 file_* 展开成 24 万个参数，超过内核参数长度上限 | 只读第一行报错 "Argument list too long" 就去查权限，没意识到是参数长度问题；跳过了「批量删除该用 find」这一步 | 批量删除一律用 find … -delete 或 xargs，不用通配符 |
| 2 | df 的统计没刷新（内核延迟） | rsyslogd 仍持有已删除文件的句柄，数据块没有回收 | 删除后立刻重复 df，把「数字不变」归因为统计延迟，没有去查谁还开着这个文件 | df 不变时第一步就 lsof +L1，而不是再敲一次 df |

### 4.2 常见坑清单

| # | 坑 | 为什么会踩 | 正确做法 |
|---|---|---|---|
| 1 | dd 写满后重启机器，系统起不来 | 根分区 100% 时 journald、systemd 写不进状态文件，卡在启动阶段 | 写满后不要重启；真进不去就回滚到干净快照 |
| 2 | mkfs.ext4 卡住不动 | 对已存在的文件/设备不加 -F 时会等待确认，看起来像死机 | 加 -F 参数 |
| 3 | rm 大日志后 df 不降 | 文件仍被 rsyslog 打开，只是目录项被删，数据块没回收 | 用 truncate -s 0 |
| 4 | lsof +L1 什么都没有，就断定「没有泄漏」 | 不加 sudo 只能看到自己的进程，root 持有的文件看不到 | sudo lsof +L1 |
| 5 | 运行状态下打快照 | QEMU 正在写盘，改元数据会损坏磁盘镜像 | 关机 → snap → 开机，三步别省 |
| 6 | fill 文件删了但日志故障注入的 500 MB 还在 | 只清理了一个故障的痕迹，没做恢复确认 | 收工前跑一遍恢复检查清单，逐项确认磁盘与基线一致 |

### 4.3 常见误判参照（值得对照自查）

- 看到写不进去就直接 du 找大文件，跳过了 df -i，在 inode 故障上白找 10 分钟
- rm 掉日志后发现空间没降，第一反应是「df 没刷新」，而不是意识到句柄未释放
- 把「日志涨得快」当成根因，没继续问「为什么涨」——真正的根因可能是某个服务在疯狂报错

## 6. 思考题解答

**Q1：df -h 显示有空间但 touch 报 No space left on device，列出三种可能并各给一条判定命令。**

三种可能：① inode 耗尽，`df -i` 看 IUse% 是否 100%（本次实测 IUse% 由 6% 涨到 23%，路径已验证）；② 文件系统只读挂载，`mount | grep " ro,"` 看是否 ro；③ 磁盘配额用尽，`repquota -a` 或 `quota -u <user>` 看是否超限。

**Q2：日志文件被 rm 掉后 df 仍显示占用，为什么？正确的清理方式是什么？**

rm 只删除目录项，文件仍被 rsyslogd 打开，数据块要等句柄关闭才回收。证据：`lsof +L1 | grep syslog` 显示 `rsyslogd 637 … /var/log/syslog (deleted)`，此时 df 前后都是 5.8 G。正确做法：`truncate -s 0 <file>`（保留 inode，立即释放块，不必重启服务）；若已 rm，则需重启持有句柄的进程。

**Q3：为什么说「磁盘满」的根因常常不是磁盘，而是某个服务在疯狂报错？如何验证这个判断？**

日志暴涨只是表征，持续刷屏的 ERROR 说明上游有服务在反复失败。验证：

```bash
journalctl --since "10 min ago" | awk '{print $5}' | sort | uniq -c | sort -rn | head
```

找出刷屏的 unit，再看该 unit 的具体报错。本次实验用 yes 模拟 500 MB 刷屏，真实场景对应「某服务每次请求都抛异常」。

## 7. 总结

| 结论项 | 结论（含数字） |
|---|---|
| 完成情况 | 完成 4 类故障实操（①②④ + 删除未释放），4 个均在 3 条命令内定位；② 只做到 IUse% 23%，未复现 100% 耗尽 |
| 效率水平 | 平均约 6 分钟，最长 12 分钟（④ 日志暴涨，含二次注入复现与 truncate 对比） |
| 主要短板 | 批量删除误用通配符导致 rm 失败；inode 实操没有用隔离的 loop 设备，直接消耗了根分区 inode |
| 改进动作 | 开工第一组命令固定为 df -h / 与 df -i / 并列；批量删文件改用 find -delete |
| 迁移场景 | 日志平台（如 Wazuh）磁盘满导致服务反复重启，直接套用「df/dfi 双命令 → du 定位 → truncate 清理」三步 |

**方法论沉淀**：

1. **先量化、再动手**——df -h 与 df -i 并用是互斥判决书，10 秒锁定故障形态，避免「删点东西试试」式穷举。
2. **清理活日志用 truncate 不用 rm**——rm 删目录项不回收被占用句柄的数据块；采集中断时先清空再重启，不删文件。
3. **批量操作不用裸通配符**——超参数长度上限时改用 find / xargs。
4. **df 不变时第一步 lsof +L1**——空间泄漏（删除未释放）最隐蔽，`lsof +L1` 的 (deleted) 输出是最硬的证据。
5. **判断空间流失是否有人为删除痕迹**——同样的 `lsof +L1`，在取证场景还能回答「空间去哪了」。
